V-модель и тесты

На этапе требований и дизайна команда планирует проверки. CI выполняет быстрые проверки при каждом изменении, а staging проверяет собранный релиз.

До PR

Продакт и QA уточняют примеры и условия приёмки. Разработчик пишет код вместе с тестами и запускает их локально.

В PR и main

Runner проверяет код и контракты на каждом изменении. Ревью оценивает архитектуру, тесты и соответствие задаче.

Перед production

На опубликованном образе проверяем готовность и критичные сценарии. Если критерий не выполнен, изменение возвращается команде.

Git, PR и версия

Git ведёт историю кода. GitHub хранит удалённый репозиторий, PR и правила слияния. GitHub Actions запускает заданные в репозитории проверки.

Маршрут из основной схемы · GitHub Flow

  1. mainбаза
  2. feature/*код + тесты
  3. Pull Requestревью + проверки
  4. mainsquash merge
git switch -c feature/catalog-filter
git add app tests
git commit -m "Add category filter"
git push -u origin feature/catalog-filter
# Открыть PR в main, пройти ревью и CI, сделать merge
git switch main
git pull --ff-only
git tag -a v2.5.0 -m "Release 2.5.0"
git push origin v2.5.0

В общем репозитории исправление обычно оформляют новым коммитом через git revert и PR. Откат работающего сервиса выполняется через CD и предыдущий digest.

От версии продукта до точного образа

2.5.0
SemVer. Исправление увеличивает PATCH, совместимая функция — MINOR, несовместимый контракт — MAJOR. Числа справа обнуляются.
v2.5.0
Git-тег. Фиксирует коммит релиза. Информация об изменениях попадает в changelog и release notes.
catalog:2.5.0
Тег в реестре. Удобное имя образа, которое технически можно переназначить.
catalog@sha256:…
Digest. Фиксирует содержимое манифеста или индекса образа. По нему разворачиваем проверенный образ.

2.5.0-rc.1 — кандидат. +build.42 — допустимые в SemVer метаданные, которые не влияют на порядок версий. Docker-тег не принимает знак +. Метаданные можно сохранить в OCI label или в release.json. При 0.y.z публичный контракт ещё может меняться.

Другие модели ветвления из лекции

Trunk-based

  1. mainкороткая ветка или коммит
  2. CIчастая интеграция
  3. mainfeature flags при необходимости

Подходит для небольших изменений и частой интеграции. Флаг управляет доступностью функции после выкладки.

Git Flow

  1. feature/*ветка задачи
  2. developинтеграция
  3. release/*стабилизация
  4. main + тегплановый релиз

Исправления релиза возвращают в develop. Срочный hotfix от main доставляют в main и обратно в develop, учитывая активную release-ветку.

GitLab Flow · релизная ветка

  1. mainповседневная интеграция
  2. release/*поддерживаемая версия
  3. тегточка выпуска

Полезно, когда одновременно поддерживают несколько версий. Команда определяет правила переноса hotfix между активными ветками. Модель можно применять и на GitHub.

Где появляется образ и где запускается контейнер

Docker помогает и на runner, и в окружении. На runner он упаковывает приложение и запускает проверку. При развёртывании runtime создаёт контейнеры из опубликованного образа.

Вариант A · сборка внутри Dockerfile

  1. Контекстapp/ и scripts/
  2. build stagedist/catalog.mjs
  3. runtime stageCOPY --from=build
  4. Docker-образготов к запуску
FROM node:24-bookworm-slim AS build
WORKDIR /src
COPY app/catalog.mjs app/catalog.mjs
COPY scripts/package.mjs scripts/package.mjs
RUN node scripts/package.mjs

FROM node:24-bookworm-slim AS runtime
WORKDIR /app
COPY --from=build --chown=node:node /src/dist/catalog.mjs ./catalog.mjs
USER node
EXPOSE 8080
CMD ["node", "catalog.mjs"]

RUN выполняется при сборке. CMD задаёт команду на запуск. .dockerignore ограничивает контекст. Для приложения с зависимостями сначала копируем манифест и lockfile, ставим зависимости, потом копируем исходники.

Вариант B · CI заранее собирает пакет

  1. Job buildсоздаёт app.jar
  2. Artifact storeхранит app.jar
  3. Job imageскачивает пакет
  4. Docker-образCOPY app.jar
Job build:     ./gradlew build
Передача:      upload-artifact → download-artifact
Job image:     docker build -t catalog:2.5.0 .
Dockerfile:    COPY app.jar /app/app.jar

Так удобно, когда тот же JAR нужен отдельным потребителям или сборка и упаковка разделены между командами. Скачиваем пакет из нужного запуска CI и кладём его в контекст сборки образа.

Три результата

app.jar или dist/catalog.mjs — файл приложения. test-results.xml — результат проверки. Образ — артефакт доставки, который публикуется в GHCR.

Собрать

docker build -t catalog:local . создаёт образ из Dockerfile и контекста. Точка означает текущий каталог.

Запустить

docker run -p 8080:8080 catalog:local запускает процесс в контейнере. EXPOSE описывает порт, а -p публикует его на хосте.

Изолировать

В Linux namespaces изолируют видимость, cgroups управляют ресурсами, а файловая система объединяет слои образа со слоем записи. Процесс использует ядро хоста или Linux-ВМ.

При выходе PID 1 контейнер останавливается и может оставаться в состоянии stopped. После его удаления слой записи исчезает. Для сохраняемых данных используют тома или внешние хранилища. Секреты сборки передают через BuildKit secret mounts, секреты среды — при запуске.

Два способа доставки

Оба пути начинаются с GitHub Actions и GHCR. Staging и production получают одну и ту же ссылку по digest. У каждой среды свои настройки.

Docker Compose на VM

Подходит для учебного стенда и сервиса на одном хосте на окружение.

  1. Actionsпубликует digest
  2. GHCRхранит образ
  3. VM stagingCompose + тесты
  4. VM productionCompose + smoke
export IMAGE_REF=ghcr.io/team/catalog@sha256:…
docker compose pull
docker compose up -d --no-build --wait

В compose.yaml у сервиса указан image: ${IMAGE_REF}. Обе среды скачивают образ из GHCR. Из staging в production передаётся только проверенная ссылка. Для отката верни предыдущий digest и снова примени Compose.

В архиве есть Compose и автоматическая репетиция на CI runner. Выкладка на свою VM описана в README.

Kubernetes + Argo CD

Подходит, если уже есть кластер и нужен декларативный rollout с репликами.

  1. Actionsпубликует в GHCR
  2. GitOps PRменяет image digest
  3. Argo CDсверяет Git и кластер
  4. Kubernetesобновляет Pod
# Фрагмент Deployment
spec:
  template:
    spec:
      containers:
        - name: catalog
          image: ghcr.io/team/catalog@sha256:…

Сначала обновляем манифест staging и проверяем rollout. Затем отдельным PR продвигаем тот же digest в production. Узлы скачивают образ из GHCR через контейнерный runtime. Для GitOps-отката возвращаем предыдущий digest в Git.

Argo CD здесь объясняет архитектуру. Для её запуска понадобится свой кластер и настройки доступа.

Continuous delivery оставляет релиз готовым к выкладке, которая может требовать одобрения. Continuous deployment автоматически доставляет изменения в production после успешных проверок.

Как собрать пайплайн для команды

У каждого этапа должны быть вход, проверяемый результат и понятное условие продолжения.

В терминах GitHub Actions. Workflow описывает запуск в YAML, job группирует шаги, step выполняет команду или готовую action, runner выполняет job. Условия on задают события, а needs — зависимости между jobs.

Повторяемость

Одинаковые команды локально и в CI, lockfiles, фиксированные версии toolchain, базовых образов и actions. Кэш ускоряет работу, артефакты передают результат.

Права и ответственность

Разработчик и QA готовят проверки, продакт согласует критерии, платформа поддерживает runner и среды, SRE помогает с SLO и откатами. Секреты выкладки доступны только доверенным jobs.

Обратная связь

Следим за логами, метриками и трассировками. VSM помогает увидеть ожидание между этапами. Метрики DORA связывают скорость доставки и стабильность.
