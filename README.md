# Каталог и учебный пайплайн GitHub Actions

**[Открыть интерактивную схему «Путь релиза»](https://povasin.github.io/devops-pipeline-lab/)**

Учебный проект показывает, как изменение проходит от требований и тестов до PR, GitHub Actions, сборки Docker-образа и выкладки. CI запускает проверки, релизный workflow публикует образ в GHCR, а Docker Compose репетирует запуск опубликованного образа по digest. Визуализация показывает весь путь, включая staging, production и откат.

В этом проекте задача CAT-17 добавляет необязательный фильтр `category` к `GET /products`. Старый запрос возвращает все три товара. `?category=lighting` возвращает товары 1 и 3. Неизвестная категория возвращает пустой список. `GET /health` проверяет, что сервер отвечает.

## 1. Проверить и запустить локально

Требуется Node.js 24. У проекта нет внешних npm-зависимостей.

```sh
node --test tests/catalog.test.mjs
node scripts/package.mjs
node dist/catalog.mjs
```

В другом терминале выполни `node scripts/smoke.mjs`. Останови локальный процесс перед проверкой Docker на том же порту.

## 2. Собрать образ и запустить контейнер

Требуется запущенный Docker с Linux-контейнерами. Точка в конце первой команды задаёт контекст сборки. В `Dockerfile` стадия `build` создаёт `dist/catalog.mjs`, а `runtime` забирает готовый файл. Команда `docker run` создаёт и запускает отдельный экземпляр образа.

```sh
docker build -t catalog:local .
docker run --rm -d --name catalog-local -p 127.0.0.1:8080:8080 catalog:local
node scripts/smoke.mjs
docker stop catalog-local
```

Если проверку запустили сразу после `docker run`, дождись запуска сервера и повтори её. `EXPOSE` описывает порт образа. Ключ `-p` публикует порт контейнера на адресе хоста.

## 3. Сделать первый PR

1. Создай GitHub-репозиторий, положи в его `main` файлы проекта и включи GitHub Actions. Дождись успешного `CI / checks` на `main`.
2. Настрой ruleset или защиту `main` с обязательными PR, ревью и статусом `checks` по названию, которое показывает GitHub. Для самостоятельной практики требование одобрения подходит, если есть второй участник.
3. Создай короткую ветку, дополни тест или документацию и отправь её в GitHub. Открой PR в `main`. В описании укажи задачу, критерии приёмки и способ проверки.
4. Посмотри результаты CI и артефакт `test-results` в GitHub Actions. После успешных проверок и требуемых одобрений сделай squash merge. CI ещё раз проверит `main`.

## 4. Выпустить версию и найти образ

После успешного CI на `main` поставь тег на согласованный коммит. `2.5.0` иллюстрирует совместимое добавление фильтра после условной версии `2.4.0`. Проект уже содержит реализацию фильтра и не включает историю `2.4.0`.

```sh
git switch main
git pull --ff-only
git tag -a v2.5.0 -m "Release 2.5.0"
git push origin v2.5.0
```

Workflow `Release candidate` проверяет тег и тесты, собирает образ, запускает его для проверок, загружает этот образ в GHCR и выгружает `release.json`. Затем `staging-check` на новом runner подтягивает образ по его digest и проверяет через Docker Compose. Этот временный стенд удаляется после прогона. Успех `staging-check` подтверждает проверку опубликованной сборки. Если пакет GHCR уже существует, проверь его права GitHub Actions на публикацию и чтение.

При красном staging останови продвижение. Исправление проходит новый PR и получает следующую подходящую версию. Сохраняй опубликованные релизы и соответствие Git-тега, коммита и digest.

## 5. Развернуть проверенный образ на своём стенде

Дождись успешного `staging-check`. Скачай `release-manifest` из этого запуска. На Linux-хосте с Docker Compose положи `compose.yaml` в отдельный каталог приложения. Из `release.json` перенеси полное значение `image` в `.env` этого каталога, в переменную `IMAGE_REF`. Для приватного пакета выполни вход в GHCR с правом чтения. Включи доступ к HTTP через локальный адрес или заранее настроенный reverse proxy.

```sh
docker compose config --images
docker compose pull
docker compose up -d --no-build --wait --wait-timeout 45
node scripts/smoke.mjs
```

Для последней команды на хосте нужны Node.js и копия `scripts/smoke.mjs`. Сохрани digest предыдущего успешного релиза. Если новая версия не проходит проверку, верни предыдущий `IMAGE_REF`, повтори `pull`, `up` и проверку. Откат образа не откатывает внешнюю БД, поэтому миграциям в реальном приложении требуется совместимая стратегия.

## Что добавить для рабочего сервиса

В этом учебном репозитории реальный staging и production подключаются к инфраструктуре команды. Для автоматизации добавь отдельные deployment jobs или GitOps, управление правами и секретами, блокировку параллельных выкладок, линтер, SAST, сканирование секретов и зависимостей, проверку образа, мониторинг и правила отката. Закрепи actions по проверенным commit SHA, базовый образ по digest и задай политику обновления. Для релизных тегов ограничь создание и изменения доверенными участниками. В больших командах платформа может вынести общие проверки в reusable workflows. Правила защищённых веток и окружений настраиваются в GitHub с учётом плана и видимости репозитория.
